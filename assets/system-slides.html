這個專案以我自己的股票資料為例，驗證在一般筆電上部署 LLM 並整合工具的完整流程。模型負責選擇工具與說明，查詢與數字計算由 Python 完成。這是個人實作驗證，企業上線經驗可以另外介紹。整份約5–7分鐘，現場 demo 另留2分鐘。

最終回答整段顯示；工具事件透過 NDJSON 傳遞04 / 09
模型不直接存取資料庫。它回傳工具名稱與 JSON 參數，Python 決定是否允許執行，再透過固定 SQL 查本機 PostgreSQL。role=tool 的結果加入訊息後，才交回模型產生回答。Ollama 的雲端功能已關閉。這裡沒有導入額外 agent 框架，目的是直接掌握訊息、工具和停止條件。

一次工具呼叫的流程

「比較 2330 和 2303 在指定期間的價格變化。」

模型回傳工具名稱與參數
compare_stocks({
  "tickers": ["2330", "2303"],
  "start_date": "2026-09-01",
  "end_date": "2026-09-21"
})
  1. 驗證代號、日期與工具白名單
  2. 查出兩檔股票的共同交易日
  3. 用首尾收盤價計算價格變化
  4. 模型依工具結果整理回答

價格變動 % =（期末收盤價 ÷ 期初收盤價 − 1）× 100

價格還原方式未驗證；結果不代表含息總報酬05 / 09
共同交易日很重要，否則可能拿不同日期比較。開發時曾發現模型誤用最近五筆行情代表整個指定期間，因此對部分價格比較問句加入檢查：若沒有使用 compare_stocks，就要求修正。這項規則有明確的語句涵蓋範圍，不能宣稱所有問法都已驗證。

執行限制與回答檢查

把可控的查詢規則放在程式中，保留核對依據。

工具執行

  • 4 個工具白名單，使用固定參數化 SQL
  • PostgreSQL 唯讀帳號與交易
  • 限制日期、筆數與工具呼叫輪數
  • 一次只處理一個問題

回答完整性

  • 期間比較需取得比較工具結果
  • 新聞摘要需包含來源 ID
  • 缺漏時要求模型修正，超限即停止
  • 保留工具結果供人工核對

這些檢查有助於攔截特定錯誤；來源正確性與摘要語意仍需核對。

新聞視為不可信資料；提示詞約束不是完整的注入防護06 / 09
將模型的自由度限制在工具選擇與文字整理。模型不能執行任意 SQL 或 shell 指令。新聞來源 ID 的檢查只確認是否附來源，不代表每個敘述都完全正確；參數化 SQL 也不等同於企業權限管理。正式環境仍要補登入、資料授權與稽核。
